# BUSIN \~Wizardry Alternative\~

日版 PS2 游戏的中文翻译，产品编号 SLPM-62098。

仓库里是译文，以及把译文做成新光盘的程序。原来的光盘不改，也不放进仓库。

## 翻译范围

- 剧本：对白、旁白、说明
- 界面：菜单、建角、商店、战斗和地名
- 术语：人名、地名、职业、种族，全篇用同一个译名
- 文字：游戏字库里没有的字用霞鹜文楷，界面用 Noto Sans SC
- 画面：需要改字的图

## 译文放在哪里

| 路径 | 内容 |
|---|---|
| `data/text/` | 剧本。一块一个文件 |
| `data/interface/` | 界面句子 |
| `data/terms.json` | 术语 |
| `data/font/` | 字库、外部字体和它们的许可 |
| `data/picture/` | 改过的图 |

这些文件由人修改。构建只读取它们，不把结果写回这里。

## 修改剧本

新开一块时，先导出原文，译文留空：

```powershell
python -m busin init-text 块号
```

译好的片段写回这一块，再对照原盘核对。同一句原文出现在别的块里时，把译文抄过去：

```powershell
python -m busin apply-text 块号 片段文件
python -m busin check-text 块号
python -m busin copy-text 来源块 目标块
```

界面、术语、字表和图片直接改上表里的文件，然后重新构建。

## 改字之前

同一个词跟 `data/terms.json` 和菜单用同一个译名。同一句日文，这一块里出现几次就译成同一句。别的文件里译过的，也沿用那句。固定译法：「気絶」译「昏迷」（不译「气绝」，避免误解为死亡）；坏状态恢复、体力恢复都译「恢复」，不写「回复」。术语的日文键照原文，半角不要改成全角。中文里的问号、叹号、逗号、句号、省略号、引号、括号用全角。夹在英文或数字里的半角照旧，比如未鉴定物品开头的 `?`。

原文没有的句号、逗号不要加。并列名词之间的「と」写成「和」。「と共に」、引用的「と」、条件句的「と」不要写成「和」。「・」照留。两句之间原文没断开，译文也不加标点。换行已经是停顿，换行处不放逗号。需要逗号时，调整断行，让逗号落在一行中间，不要放在行首。原文那一行末尾没有句号，译文行尾也不加。省略号按原文里「…」的个数写。一个就写一个，不要写成「……」。两个、三个也照原数留，比如「1000……」是两个，「………」是三个。

同一角色的口吻全篇一致。拟声词跟原文的字数。阴沉的低笑「クク」写成「咯」，几个字就写几个。

有的界面句子只是后半句，人名另画在前面，最后一个字贴着这句。原文开头的「は」不用译出来。比如「は死んでしまった!!」译成「死了！！」，画面上就是「奥斯卡死了！！」。原文的「たち」「達」写成名字后面的「他们」。比如「達は逃げられない!!」译成「他们无法逃跑！！」。

译文行尾不用自己补满，打包时补上。原文中间空着的格子里没有字，不要补一个词进去。物品操作原文开头那个「0」是往右挪一格，译文里不要写。

两个字的标签中间空一格，用来和三个字的对齐。种族、阵营、职业、能力、物品命令都这样。术语表里的词是紧挨着的，不要互相改。起名画面的「确定」「返回」也是紧挨着的。

## 剧本怎么排

剧本在 `data/text/`。每条有 `type`，没有 `width`。一行最多多少格，由 `type` 决定。文件开头的 `align` 不管这一条是对话框还是过场，只管行首空格怎么读。`left` 时行首空格是缩进，`center` 时算进这一行。导出时已经设好，不要改。

`center` 是居中的过场，每行最多 19 格。`dialog` 是对话框。文字最多 19 格，第 20 格是行尾图标，不在这 19 格里。再扣掉这一行的行首排版。`source` 会把行首排版显示成标记或空格。译文只按自己行首写的排版，不写就没有行首排版。每行还能写几个字，用 `python -m busin check-text 块号` 看。它印出对话框每一行的已用格数和上限，没译的只印上限。检查通过只说明没超出上限。`subtitle` 是字幕，每行最多 21 格。

一个字占一格，一个空格也占一格。说话人、引号、标点都算。剑士加前引号是 3 格。尖括号里的标记不占格。行首排版以外，整句里这些标记的种类和先后要和原文一样。可以改它包住哪几个字。少一个、多一个、对调或者换成别的，打包会停。

`source` 里的 `\n` 是原文换行。`text` 每一项是一行，空字符串是空行。原文有空行就留着。译文行数跟原文一样。两三行并成一行，就算顶满 19 格也能通过检查，换行的停顿却没了。不要在一项里面写 `\n`，也不要写 `/`。`/` 只用于界面的格子说明。下一项接着画到下一行。

`<BREAK>` 写在两句话中间，也是换行，后面的字接着画。写在这一段的最后，是等玩家按键，不再多空一行。停顿前后分开数格子。

```text
一边啃着，一边等。<BREAK>信着母亲的话，静静地等。<BREAK>
```

前一句、后一句各自不能超过这一行的格数。最后那个停顿只是等按键。

| 标记 | 画面上 |
|---|---|
| `<PAGE>` | 主人公的名字 |
| `<FE00>` | 刚报上名的那个人 |
| `<FFF0>` 到 `<FFF5>` | 六个队员，用来列「谁来」 |
| `<STYLE:0>` 到 `<STYLE:7>` | 换一种画法 |
| `<FFC0>` 到 `<FFC9>` | 选项行号 0 到 9，写行首排版时要原样保留 |
| `<FC00>` 到 `<FC0A>` | 字的大小。`<FC00>` 是平常大小 |
| `<FB01>` … `<FB00>` | 把中间的字标出来，比如物品名和金额 |
| `<FB06>`、`<FB07>`、`<FB09>` | 标出来的字用哪种颜色 |
| `<FB03>` … `<FB02>` | 中间的字会抖 |
| `<FB04>`、`<FB05>` | 抖得更厉害，很少见 |
| `<FD00>` 到 `<FD14>` | 打字多停一下，不换行。`<FD14>` 停得最短 |
| `<FFD0>` 到 `<FFDF>` | 往右空出 1 到 16 格 |
| `<F010>`、`<F025>`、`<F031>` | 插入一个效果 |
| 以 `B0`、`E0` 开头的 | 写在目录、日记的条目前面 |

`<FFD0>` 空 1 格，后面每档多 1 格。`source` 和译文都把它写在一行最前面；写在句子中间时，会显示成这个标记。对话框原来的行首空格在 `source` 里显示为空格。

对白续行如果原文用缩进对齐说话人，译文不要照抄原缩进档位，要按译文第一行到「的格数重新换算。原文另有特殊缩进的，保留原文档位。

`source` 显示这一行原有的行首排版，`text` 每一项的行首排版完全以译文自己写的为准。不写标记或空格就没有行首排版；要保留 `source` 的排版，就把那里的标记和空格一起复制过来。选项行号不能改。字和字中间的空格会写在原文里，译文里要留就自己写上。行尾的空格不写进原文。

## 界面怎么排

界面句子在 `data/interface/`。每条有原文 `source` 和译文 `text`。有的还有 `type` 和 `width`。

`width` 是这一条占多少格。`15x3` 是每行 15 格、共 3 行。`3` 是一行 3 格。

一格空写成一个空格。两格及以上写成 `{2}` 这样。原文的行首、行尾空格都留着，用来对照。译文的行尾不用自己补满，打包时补上。译文里写了行首空格，画面上就会缩进。

`type` 是 `grid` 的，是一块固定格子。装备说明、连携、羊皮纸、职业、能力、性格、种族、阵营、存档提示都是这种。译文里不写 `/`，整段按每行的格数往下排，词中间也会被切开。写了 `/`，一段就是一行。某一行超过行宽会报错，多出来的字不会掉到下一行。行数不够，剩下的行是空的。行数多了也会报错。

连携是 15 格乘 3 行。译文写成：

```text
前卫3人对敌1体一口气攻击。/能造成比平时更多的伤害
```

第一行正好 15 格。第二行 12 格，末尾补 3 格。第三行空着。

`type` 是 `line` 的只有一行。创角、转职、物品操作、阶级、存档位、城镇、委托、喊话都是这种。这里的 `/` 不是换行。超过 `width` 会报错，短了只在行尾补空格。

没有 `type` 的是菜单、商店、房间这类，长短不固定。菜单、商店、调试菜单、旅馆里的 `/` 是另一处换行，写到哪儿算哪儿，不按上面的行宽检查。

委托标题在 `data/interface/places.json`，其中的 `/` 也表示换行。装备效果说明在 `data/interface/blurbs.json`，固定说明按每行 17 格、共 3 行处理；一整条说明保存在同一项里，中间的空格不是另一条说明的起点。

## 修改图片

图片清单是 `data/picture/images.json`。不带 `.zh` 的 PNG 用来对照原图，构建读取对应的 `.zh.png`。`menu/` 放菜单小图，`town/` 放城镇招牌，`title/` 放标题画面，`generated/` 放清单中由程序生成的图片。干净底图统一放在 `data/picture/templates/`，原来的 `backgrounds/` 已改名。

菜单文字的原文、译文、尺寸、调色板和排版写在 `busin/picture_text/menu_text.py` 的 `LABELS` 里；带横幅背景的两张由 `busin/picture_text/cock.py` 绘制。`busin/picture_text/registry.py` 记录每个清单条目用哪个渲染器，缺少记录会在导出或构建时停下。改译文时，也要同步清单里的 `text`。

`switch` 与 `page_switch` 共用纹理中的文字。清单里的原始 rect 用来导出原盘对照图；`reuse` 的 `name` 指定同一纹理中的来源，`x`、`y` 是相对来源译图的像素偏移。`switch` 从 `(32, 0)` 起裁出 48×16 的译图，构建时同步修改游戏取样位置，绘制尺寸和屏幕起点保持原样。复用来源不能再复用其他小图。

只编辑或生成 `page_switch.zh.png`，随后运行 `export-pictures`，就会自动更新 `switch.zh.png`，已有的派生图也会覆盖。构建会检查派生图与来源对应区域完全一致；有差异时会停下来提示重新导出。

改了文字、底图或绘制代码后，要先重新生成 `.zh.png`，再构建光盘。单独运行 `build` 不会重画这些菜单图片。

```powershell
python -m busin export-pictures
python -m busin export-pictures --force-zh
```

第一条导出原图，补齐缺少的译图；有绘制规则的菜单小图若译图仍与原图相同，也会生成译图。第二条会重新生成所有由程序绘制的译图，覆盖这些已有的 `.zh.png`。执行后先检查图片差异，再构建。

## 做出光盘

把日版原盘的路径写进仓库根目录的 `config.toml`，例如 `disc = "games/game.bin"`。相对路径从仓库根目录算。这个文件不提交。没有它时构建会停，读盘测试会跳过。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
python -m busin build
python -m pytest tests -q
```

构建前想看余量，运行 `python -m busin plan`。它会列出台词进度、每个字库槽的剩余格数、每个块的扇区预算，以及还没翻译的块之后要改成整段打包。

构建后再运行 `python -m busin audit-image`。它会核对报告里的输入和成品，再把原盘与成品按扇区对齐，确认除了报告声明过的改动没有别的改动，并写出 `build/image/change-audit.json`。

`build/image/report.json` 记录构建时的提交号、输入文件和成品的校验值。工作区有未提交改动时，提交号只表示基于哪次提交构建，不能单靠它还原成品。镜像改动的类别、范围和排除项见 [光盘镜像改动分类](docs/disc-image-changes.md)，其中的数字对应文首注明的构建快照。

成品是 `build/image/busin-zh.cue`。用它从头开机。同样的输入，每次构建得到的光盘字节相同。从头开机确认后，再给对应提交打 tag，并在 `CHANGELOG.md` 记录这一版的差别。
